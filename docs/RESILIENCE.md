# 自愈与观测

这份文档记录两件事，以及它们背后的**实测依据**：

1. **自愈**：内核与隧道出问题时，程序自己做什么、什么时候不做。
2. **观测**：出问题时用户能看到什么，以及每一层证据各自回答什么问题。

之所以要单独写一份：这些行为大多是「看不见的」——用户只在出问题时才察觉，
而维护者如果不知道当初为什么这么定，很容易把它当成多余逻辑删掉，或者把已经
验证过的结论再验证一遍。**每一条实测结论后面都写了方法和数字**，附带的表格
里还列了「评估过但不采纳」的项，那是为了不再重复踩。

---

## 一、自愈：三条链路

内核出问题有三种截然不同的形态，程序分别处理。它们的共同点是**绝不静默**：
要么给出结论，要么给出「我已经尽力了」。

### 1. 内核进程退出了（明确的崩溃）

由子进程的退出回调触发，交给 `CrashRecovery`（`app/lib/core/reconnect.dart`）裁决。

| 情形 | 处置 | 依据 |
| --- | --- | --- |
| 用户点了断开 | **绝不重连** | 退出回调是拆内核时触发的，不区分就会变成「断开之后自己又连上」 |
| 启动后 10 秒内就退出 | 最多重试 2 次 | 这种几乎必然是配置或环境问题，重试解决不了，快速失败更有用 |
| 稳定运行 30 秒后退出 | 单次事故最多重试 5 次 | 属于偶发事故，重试额度重新计算 |
| 累计重试达到 10 次 | 停止，并说明原因 | **这一条是必需的**：上面「稳定运行过就算新事故」的规则会重置单次额度，一个「每跑两分钟崩一次」的内核会被无限重连下去 |

重试间隔按 2 的幂退避：1s、2s、4s、8s、16s…单次上限 30s。刻意不加抖动
（jitter）——抖动是给「大量客户端同时重试」用的，这里是单机单内核，加了只会
让等待时间变得不可预测、不可测。

### 2. 隧道不通了（内核活着，但出不去）

`CoreMonitor` 每 15 秒探测一次隧道（经内核访问 `https://www.gstatic.com/generate_204`，
量的是端到端耗时而不是 ping 服务器 IP）。连续失败 3 次后做**健康判定**：

| 对照结果 | 结论 | 处置 |
| --- | --- | --- |
| 直连正常 | `tunnelDown` | 重启内核 |
| 直连也不通 | `networkDown` | **不重连**，只提示 |

拿直连做对照是这一步的关键：两者表现完全一样，处置方式却相反。本地网络断了
的时候重连只会空转。

### 3. 内核卡住了（连看都看不到它）

Clash API 监听在回环地址上，**不受外网影响**。连续 5 次采样读不到它（轮询周期
1 秒），说明内核进程自己卡住了，判定为 `coreUnreachable` 并重启。

这一条**不做直连对照**：回环上的失败与本地网络无关，拿直连去判断只会把结论带偏。

在它之前，这种状态是完全静默的：界面照旧显示「已连接」，速率和连接数停在几分钟
前的数字上，用户只会觉得「网速怎么不动了」。

### 重启的限流

第 2、3 条都会重启内核，但重启必须克制：如果根因是节点已经下线，重启就成了每次
重新握手的无效循环。因此有 `HealthRecoveryGuard`：**一次连接内最多因健康问题重启
2 次，两次之间至少间隔 2 分钟**。额度用尽时明确告诉用户「自动恢复次数已用尽，
请手动重连或更换节点」。

隧道恢复正常只**归还次数、不清除冷却时间戳**——否则「断了又通、通了又断」会把
额度反复重置成无限重连。

### 端口被占用时自己换

混合入站与 Clash API 默认用 2080 / 2081。被占着时（上次被强杀残留的内核、另一个
VPN 客户端、用户自己的服务）内核会直接启动失败，而错误信息是一句 curl 风格的绑定
失败加一句「内核启动超时」，用户完全看不懂。现在会往后找第一个可用端口
（`app/lib/core/port_allocator.dart`，最多搜索 50 个），并如实提示「默认端口 2080
被占用，本次改用 XXXX」。

探测与真正绑定之间存在时间差，理论上仍可能被抢走；这一层不追求绝对，只把
「本来一定会失败」变成「绝大多数情况下自己就好了」。

## 二、观测：四层证据

界面上的每一处诊断都有明确分工，不是越多越好——**同一件事说两遍会把真正的
问题淹掉**。

| 入口 | 回答的问题 | 数据来源 |
| --- | --- | --- |
| 状态卡片 · 失败摘要 | 「打不开」是规则判错了还是节点不通 | 内核日志里的连接失败，按出站归类 |
| 状态卡片 · 失败详情 | 哪些目标失败了、各失败几次、我该做什么 | 上一项的分组视图，可一键「改走代理」 |
| 状态卡片 · 内核日志 | 内核自己写的原始记录 | 500 行环形缓冲（两端共用） |
| 状态卡片 · DNS 明细 | 每个解析器各自多快、失败过几次、直连与隧道差多少 | 每 45 秒一轮的探测窗口（`ResolverHealth`） |
| 状态卡片 · 隧道握手 | 「连不上」是**未被服务端受理**还是**数据面问题** | 内核 DEBUG 日志里的 WireGuard 握手里程碑 |
| 分流记录页 · 查证域名 | **这一个**域名怎么了 | 分流记录 + 规则表 + 两路 DNS 对照 |

几条刻意的边界：

- **日志不是错误。** 日志到达会让界面刷新，但不会写进错误提示——绝大多数行都
  不代表出错。
- **DNS 这一行的颜色与文字必须说同一件事。** 告警门槛（连续 3 次失败）与结论门槛
  共用同一个常量（`ResolverHealth.downThreshold`）。此前颜色用的是「任意一次失败
  就变黄」，而文字要连续两次全失败才说异常——于是最常见的画面是**文字写着「一致」、
  整行却是黄的**。探测走明文 UDP，丢一个包很正常，用户却只能得出「这软件一直报错」，
  然后去改一个本来没问题的设置。`test/dns_row_state_test.dart` 锁定这两个门槛一致。
- **握手行要靠 DEBUG 级日志才有。** sing-box 把 wireguard-go 的 `Verbosef`
  映射到 `Logger.Debug`，因此配置里的 `log.level` 一旦是默认的 `warn`，握手
  里程碑根本不会产生——解析器再正确也永远读不到，界面只能停在「正在读取内核
  握手状态…」。现在由 `ParsedProfile.wantsDebugLogs` 按协议下发：只有 WireGuard
  调成 debug，其余协议保持 warn，避免把日志缓冲刷成噪声。这条链路两端共用，
  因此 PC 与移动端的行为必然一致；`test/wireguard_handshake_e2e_test.dart` 用
  真实内核锁定「日志真的会被产生」。
- **失败详情只对「疑似规则未覆盖」的组给出「改走代理」。** IP 目标、走隧道仍失败
  的目标都不给这个入口，因为改了也没用；标签颜色也据此区分（琥珀＝我们能改，
  红色＝只能换节点，蓝色＝与规则无关）。
- **查证域名不预测分流结果。** geosite-cn 是二进制规则集，Dart 侧读不了（标准库
  没有 zlib），因此「这个域名会不会命中规则库」在客户端根本答不出来。与其编一个
  看起来像预测的结论，不如只说已经发生的事实。
- **`/connections` 只包含还活着的连接。** 观测引擎按秒轮询它，因此两次轮询之间
  生灭的连接不会出现在分流记录里。这是这套观测方式的固有限制，不是缺陷。

## 三、实测结论

以下都是在本机用**真实内核**跑出来的，方法写在数字后面。列在这里是为了不再重复。

### 采纳的改动

| 项目 | 结论 |
| --- | --- |
| **TUN 入站 MTU** | sing-box 的 tun 入站默认 MTU 是 **9000**（官方文档），而隧道只能装下 1420（WireGuard）/ 1500（OpenVPN）。两者不一致时系统栈会按 9000 组 TCP 段，进隧道后被迫在 IP 层分片，一个大包裂成六七个 UDP 包——吞吐下降、延迟抖动，**且内核不报任何错**。现在 TUN MTU 由协议适配器给出（`VpnProtocolAdapter.tunMtu`），与端点用同一个函数计算，避免两处漂移 |
| **等内核就绪的轮询节奏** | 内核从启动到 Clash API 能应答只要 **520–610ms**（4 组独立启动实测）。原先固定 300ms 的间隔意味着探测点落在 0/300/600/900ms 上，于是**每一次连接都白等平均约 120ms、最坏约 290ms**——与内核无关，纯粹是客户端自己的定时器。改成开头 25ms 密集探测后，实测已基本等于真实就绪时刻 |
| **握手状态依赖的日志级别** | 同一个 WireGuard 配置，`log.level=warn` 时内核输出 **0 行**，`log.level=debug` 时输出 **65 行**（含握手里程碑）。因此把 `log.level` 写死成 `warn` 等于让「隧道握手」这一行永远读不到数据。现在按协议下发（WireGuard=debug，其余=warn），并用真实内核在 `test/wireguard_handshake_e2e_test.dart` 锁定 |
| **DNS 探测的绑定地址** | UDP 探测套接字**必须绑通配地址**。绑回环（`127.0.0.1`）会让报文带着环回地址作源地址、对外查询**瞬间**失败（实测 1–9ms 就返回，而不是等满 3 秒超时）。症状是界面长期显示「国内解析异常」并建议更换解析器，而同一时刻系统自带的 `nslookup` 查同一个服务器完全正常——用户怎么改都改不好。对照实测：`bind 127.0.0.1` → 失败；`bind 0.0.0.0` → 成功 `183.2.172.177`（12–13ms）。修好后同一环境下两个国内解析器的实测耗时是 **6–17ms**、告警消失。`test/dns_probe_reachability_test.dart` 用真实网络锁定 |

### 评估过但不采纳

| 项目 | 结论与方法 |
| --- | --- |
| **DNS 缓存配置**（`dns.cache_capacity` / `dns.independent_cache`） | 同一域名连查 6 次：不下发缓存配置是 19.5/4.9/5.7/5.1/5.9/5.2 ms，下发 4096 容量并开启独立缓存是 15.8/5.8/4.8/6.1/4.8/5.2 ms——**无可测差异**，内核自身已经在缓存 |
| **嗅探（`{action: sniff}`）的时延代价** | 担心过「客户端等服务器先开口」的协议（SSH、SMTP、部分游戏）没有包可发，嗅探只能等到超时。实测否定：本机起内核 + 一个「一 accept 就发问候」的 TCP 服务，经 SOCKS5 量首字节——不开嗅探 1/1/1/1/1/3 ms，开嗅探 1/1/1/1/1/1 ms，嗅探 50ms 1/1/2/2/3/3 ms。**不要**为了「提速」去调小嗅探超时，那只会让慢一点的客户端认不出域名，从而按 IP 误判分流 |
| **直连出站的 `tcp_fast_open` / `tcp_keep_alive`** | 内核接受这两个字段（`sing-box check` 已验证），但收益仅为「直连 TCP 少一个 RTT」，且 TFO 在部分中间设备上会被丢弃。要做的话先补一条可对比的时延基线 |

## 四、账号密码

OpenVPN 的 `auth-user-pass` 配置必须带服务端分配的用户名与密码，而它们不在配置文件
里。导入这类配置时程序会就地弹出表单（三个导入入口与命令行/安卓分享都走同一个收口
点），也随时可以在「配置」列表里补填或修改。

落盘方式按平台：

| 平台 | 方案 | 说明 |
| --- | --- | --- |
| Windows | **DPAPI**（`crypt32.dll`，FFI 直调，无原生插件） | 密钥由当前 Windows 账户派生。换账户或换机器就解不开——这是特性而不是缺陷 |
| 安卓 | **未加密**，并在表单里如实写明 | Keystore 尚未接入。与其写个自制混淆制造「已加密」的错觉，不如明确地不加密并告诉用户 |

账号与密码**打包成一个整体**再加密：只加密密码而把账号明文写在旁边，等于告诉任何
读到文件的人「谁在用这台机器上的哪个账号」。

凭据取不回来时（换机器、换账户），配置**照常保留**，只是标记为「待补填」并提供一个
填写入口。这一点是刻意设计的：早先的实现在凭据缺失时直接让解析失败，而恢复流程对
解析失败的处理是跳过这份配置——用户看到的是「我导入的配置不见了」。

## 五、退出与释放：为什么这块要单独讲

这一节回答一个很具体的问题：**用户关掉应用之后，机器还会不会带着我们的痕迹。**

之所以值得单列：这里的失败**用户在界面上看不到**。代理没还原、内核没结束，界面
关闭之后一切「看起来正常」，只是所有网站都打不开——而没人会把这件事和 VPN 联系
起来。因此这里把「哪条路径负责什么」写清楚，并给出每一条的验证方式。

### 5.1 五条退出路径，各自覆盖什么

| 路径 | 触发 | 还原系统代理 | 结束内核 |
| --- | --- | --- | --- |
| 点圆环断开 | `disconnect()` | ✅ | ✅ |
| 点标题栏关闭 | 收进托盘，隧道**继续运行** | 不适用（本来就不该还原） | 不适用 |
| 托盘「退出 XVPN」 | `WM_DESTROY` | ✅ | ✅ |
| 注销 / 关机 / 重启 | `WM_ENDSESSION`（wparam≠0） | ✅ | ✅，随后主动退出 |
| 崩溃 / 任务管理器强杀 | 无可执行代码 | ❌（下次启动兜底） | ✅（作业对象） |

四条设计要点：

* **`WM_DESTROY` 是清理的唯一收口。** 托盘「退出」走的是 `DestroyWindow`，因此
  只需在这一处做清理，新增退出入口时不会漏掉某一步。
* **关机只看 `WM_ENDSESSION` 且要求 `wparam` 非零，不在 `WM_QUERYENDSESSION` 里
  清理。** 前者只是「能不能关」的询问，任何一个应用都能否决它；在那里清理会把一个
  仍在运行的隧道留下「界面显示已连接、系统代理却没了」——用户以为在走隧道，实际
  全在直连。关机被取消时会收到 `wparam` 为零的 `WM_ENDSESSION`，那时不清理。
* **清理后立刻主动退出，不等系统来结束我们。** 否则 Dart 侧的自愈逻辑会把「Clash
  API 读不到」判定成内核卡死，在系统真正杀掉进程之前的几秒里把内核**又拉起来一次**。
* **强杀连不到代码，用作业对象兜底。** 进程被放进一个带
  `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的作业，内核作为子进程自动成为成员；本进程
  无论以什么方式结束，系统都会把它一并收走。这条覆盖了此前完全无人处理的两条路径
  （崩溃、任务管理器结束任务）。

### 5.2 系统代理的三条安全规则

* **备份只在还原成功后才消费。** 反过来（无条件删）有一个很难查的后果：万一写注册表
  失败（权限、组策略），备份没了、代理却仍指着已退出的内核，下次启动再也无从恢复。
* **退出清理开始后，一切新的代理接管请求都变成空操作。** Dart 的连接流程是异步的，
  「等待内核就绪 → 设置系统代理」可能正好排在退出清理之后完成——那样会把刚还原好的
  代理重新写回一个死掉的端口。
* **还原失败必须出声。** 这一步失败意味着用户的网络仍然是坏的，而现象与隧道无关。
  界面会明确提示去「设置 → 网络和 Internet → 代理」里关掉手动代理。

### 5.3 只允许一个实例

系统代理是**全局且唯一**的一份设置。两个实例各自接管一次，后启动的会覆盖前一个；
此后关掉任意一个，它的还原逻辑都会把代理改回用户原本的取值，而另一个实例的内核还在
运行——表现为「隧道显示已连接，但所有网站都打不开」。因此第二个实例会把已有窗口唤到
前台然后直接退出。

### 5.4 配置落盘的原子性

`AppStore.save` 先写 `.tmp` 再改名，因此**写入过程中被杀掉不会留下半截 JSON**。
读到空文件或损坏内容时返回空表而不是抛错——最坏是回到「重新导入」，不该让应用起不来。

### 5.5 怎么验证

| 项 | 方式 |
| --- | --- |
| 接管 / 还原配对、还原失败提示 | `test/proxy_cleanup_test.dart`（注入假代理，跑真实内核） |
| 断开后进程与 PID 文件收干净 | `test/connect_path_test.dart` |
| 单实例、关机清理、强杀不留孤儿 | 手工：启动 → 看注册表与进程 → 发 `WM_ENDSESSION` / 强杀 → 再看一次 |

## 六、已知限制

诚实清单，不是待办列表：

- **安卓还不自愈重启。** 健康检测两端共用，但只有 Windows 端会重启内核。安卓侧的
  重启要走 `prepareVpn`，需要确认它在自动重启时会不会弹出系统授权框——**这一步只能
  在真机上验证**。
- **桌面端没有 TUN。** 它需要 wintun 驱动与管理员权限，因此不提供这个选项，而不是
  提供一个选了不生效的开关。
- **不预测分流结果。** 见上文（二进制规则集读不了）。
- **观测是采样的。** 连接列表按秒轮询，转瞬即逝的连接看不到；DNS 与自检结论也是
  采样值，会随时间变化，因此各自给了「重测」入口。
- **强杀之后的代理要等下次启动才还原。** 被强杀时没有任何代码可以执行，只能依赖
  下次启动的 `recoverIfNeeded`。这期间用户的网络是不通的——除非另起一个常驻进程来
  盯着，而那与「零依赖、免安装」的定位冲突，因此不做。
- **被强杀时留下的内核由作业对象处理，但若作业对象创建失败**（极老系统或已被别的
  作业占用），退回「退出时枚举子进程」那条路径，此时强杀会留下孤儿内核——它会被
