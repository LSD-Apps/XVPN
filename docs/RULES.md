# 分流规则：完备性与检测能力

本文记录对内置规则库的实际测量结果，以及程序在规则不全时的应对方式。
所有数字都是实测得到的，不是估计。

## 一、内置了什么

| 规则库 | 内容 | 体积 |
| --- | --- | --- |
| `geosite-cn` | 591 个精确域名 + 8597 个域名后缀 + 8 条正则 | 55 KB |
| `geoip-cn` | 5742 个 IPv4 网段 + 2134 个 IPv6 网段 | 34 KB |

两者都从上游 `SagerNet/sing-geosite`、`SagerNet/sing-geoip` 的 `rule-set`
分支获取，经 jsDelivr CDN 下载（GitHub 直连在部分网络下时通时断）。

复核命令：

```
sing-box rule-set decompile assets/rulesets/geosite-cn.srs -o geosite.json
sing-box rule-set match -f binary assets/rulesets/geosite-cn.srs www.baidu.com
```

> 注意 `match` 子命令默认按 JSON 解析，读 `.srs` **必须**加 `-f binary`；
> 另外它用**输出文本是否为空**表示结果，而不是退出码——这两点都踩过坑。

## 二、完备性：够用，但不完备

### 抽样结果

* 主流、预期命中规则集的站点 28 个：全部命中
* 预期未命中规则集的站点 18 个：全部未命中（含 `google.com`、`github.com`、`cdn.jsdelivr.net`）
* 命中与未命中的 IP 各 5 个：全部正确

### 长尾实测

拿 25 个二线/垂直类站点测试，**域名表只覆盖 21 个（84%）**：

```
www.gaoding.com        未命中   解析 192.0.2.173   geoip-cn 命中 → 仍会直连 ✓
www.jianyu360.com      未命中   解析 192.0.2.239   geoip-cn 命中 → 仍会直连 ✓
www.gelonghui.com      未命中   解析 192.0.2.37     geoip-cn 命中 → 仍会直连 ✓
```

### 关键结论：IP 表只对「目标本身就是 IP」的连接起兜底作用

> **本节曾写错，已按实测更正。** 原文的结论是「域名没命中时内核会先解析域名、
> 再拿解析结果去匹配 `geoip-cn`，因此长尾站点仍会走直连」。**这一步不会发生**，
> 见下面的实测。

#### 实测（受控，用随包内核）

方法：把内核配置里的 `vpn` 出站换成一个必然连不上的 socks 出站，在本地跑随包
`sing-box.exe`，只观察**路由判定**，不产生任何到真实服务器的流量。这样「走了哪条
路」由内核日志直接给出，不靠推测。

| 目标 | 内核日志 | 判定 |
| --- | --- | --- |
| `www.baidu.com`（命中 `geosite-cn`） | `match[3] rule_set=[geosite-cn geoip-cn] => route(direct)` | 直连 ✓ |
| `114.114.114.114`（IP 字面量，在索引内） | `match[3] rule_set=[geosite-cn geoip-cn] => route(direct)` | 直连 ✓ |
| `8.8.8.8`（IP 字面量，不在索引内） | `outbound/socks[vpn]` | 隧道 ✓ |
| `www.gaoding.com`（域名，未命中 `geosite-cn`） | `match[0] => sniff` → `sniffed domain` → 直接 `outbound/socks[vpn]`，**全程没有任何 DNS 解析** | 隧道 ✗ |
| `www.jianyu360.com`、`www.gelonghui.com` | 同上 | 隧道 ✗ |

关键在最后三行：**判定过程中没有发生任何域名解析**。也就是说，`ip_cidr` 类规则集
（`geoip-cn`）在**域名目标**上不会参与判定——sing-box 1.14 不会为了让路由规则
匹配而自动解析目标域名（要解析必须显式用 `resolve` 动作，见下）。

#### 因此准确的说法是

| 连接形态 | 直连判定依据 | 是否有兜底 |
| --- | --- | --- |
| 域名（绝大多数流量，`sniff` 能认出域名） | **只有 `geosite-cn`** | **没有** |
| IP 字面量 / 嗅探不出域名的流量 | `ip_is_private` + `geoip-cn` | 有 |

即：**「双保险」只对 IP 形态的连接成立**。域名一旦不在 `geosite-cn` 内，就**必然**
进隧道，没有 IP 层兜底。40 个国内站点的实测里 37 个命中、3 个漏出（7.5%），
漏出的那 3 个全部进了隧道。

#### 一个看似可行的修法，及其代价

在规则集判定之前插一条 `{"action": "resolve", "server": "dns-cn"}`，可以让
`geoip-cn` 拿到**直连解析**的结果再做判定。实测有效：那 3 个漏网站点全部转为直连，
且 `google` / `youtube` / `twitter` 仍走隧道（未被误判直连）。

**但它有副作用，因此没有采纳**：`resolve` 会**替换目标**，对要送进隧道的流量
同样生效。日志里 `www.google.com` 的目标被替换成了国内解析出的 `174.132.167.252`
和一个明显被注入的 `2001::1`——被墙站点会带着国内解析（可能被污染）的地址进隧道，
反而可能打不开。

改用**域名清单**（见下节「应用直连预置」的思路）来补覆盖率则没有这个问题：
域名清单不依赖解析结果，也就不会被污染影响。

## 三、两个真正兜不住的方向

| 情况 | 后果 | IP 表能否补救 |
| --- | --- | --- |
| 域名不在 `geosite-cn` 内（长尾国内站点、境外应用） | 必然进隧道：慢、白耗带宽，出口 IP 也变成境外的；**不报错**，用户看不出原因 | **否——`geoip-cn` 对域名目标不参与判定**（见上节实测） |
| 站点解析到 `geoip-cn` 之外的地址（企业异地部署、套用规则集外的 CDN） | 被送进隧道：慢，且部分服务会因地域限制失败 | 否 |
| 判为直连的主机解析到 `geoip-cn` 内的地址、却并不真的可达 | 判为直连 → **直接打不开** | 否，反而有害 |

第二种概率低，但一旦发生就是「网站打不开且用户完全看不出原因」，
是最需要检测能力介入的场景。第一种则相反：它**不会**表现为打不开，而是安静地
浪费隧道带宽，因此需要的是**可观测**（第四点七节的「隧道流量去向」）
与**反方向纠正**，而不是失败归因。

## 四、程序具备的检测能力

### 已实现：失败归因

内核在失败日志里写明了走的哪个出站，这是区分两类问题的唯一可靠信息：

```
ERROR connection: open connection to www.google.com:443
  using outbound/direct[direct]: dial tcp ...: i/o timeout
```

`lib/core/core_log.dart` 解析这类日志，得到 `(目标, 出站, 原因)`，并据此判断：

* **判为直连却失败** + 目标是域名 + 不是解析失败 → 疑似规则库未覆盖；
* 走了隧道却失败 → 节点/服务器问题，改规则没有意义；
* IP 目标失败 → 与域名规则无关，不归咎于规则。

界面上落在「零配置接管状态」卡片里，用琥珀色（疑似规则问题）与红色（节点问题）
区分，并给出下一步建议。

### 已实现：规则库可更新

规则库在运行时从程序内的出厂副本复制到可写目录
（`%LOCALAPPDATA%\XVPN\rulesets`），「检查更新」会真的从上游拉取新版本并覆盖。
下载后校验 `.srs` 魔数，采用「先写临时文件再改名」避免半截文件让内核起不来。

### 已实现：本地自动纠正表

同一域名「判为直连却失败」达到阈值后，自动把它加入强制代理列表，并以
**最高优先级**注入路由规则。这是让「傻瓜式」闭环的一步：用户不需要理解规则，
程序自己学会。

实现见 `lib/core/auto_route.dart`，注入点在 `lib/core/singbox_config.dart` 的
`_route()`——学到的规则插在 `sniff` / `hijack-dns` 之后、`geosite-cn` /
`geoip-cn` **之前**。位置是关键：需要纠正的场景恰恰是规则库「正确地」判成了
直连（域名解析到 `geoip-cn` 内的地址，命中了规则集），把规则放在规则库之后它永远不会生效。

设计上的保守之处：

| 约束 | 取值 | 理由 |
| --- | --- | --- |
| 触发阈值 | 连续 3 次「没有交付」 | 单次失败可能只是抖动，一次就改路由会让用户觉得「时好时坏」 |
| 解析结果不一致 | 1 次即可 | `DnsVerdict.suspectPoisoning` 是确定性证据，不必再等 |
| 反证 | 一次「确实交付」即清零 | 既然直连真的把内容送出来了，当初的判断就不成立 |
| 撤销 | **连续** 3 次「确实交付」 | 见下：坏时段里成功是偶尔插进来的，用累计计数会来回横跳 |
| 只作用于域名 | IP 目标一律不动 | IP 层面的失败与域名分流规则无关 |
| 容量 | 400 条 + 14 天衰减 | 不会变成一个只增不减的黑名单 |

> **阈值是「连续 3 次」，不是「累计 3 次」，更不是「1 次」。** 这三点都必须成立：
>
> * **1 次**：未定性的证据**不建表项**（见 `AutoRouteTable._pendingSetbacks`）。
>   一旦建项，`buildRouteRules()` 会立刻按它的 `preference`（默认 `forceProxy`）
>   生成规则——「连续 3 次才纠正」就变成了「一次抖动就推进隧道」。这条在
>   反方向纠正里一开始就规避了，失败方向原先没有，是本轮补上的。
> * **累计而非连续（撤销方向）**：实测 github.com 在坏时段里失败**成簇**、成功
>   偶尔插进来。用累计计数，两次侥幸成功就足以撤销刚学到的规则，规则因此反复
>   推翻又重建。改用连续计数后，交替出现的成败永远攒不满阈值，规则稳定；而网络
>   真的恢复时连续成功很快攒够并撤销——迟滞是自动的。
> * **观测的限流**：同一域名的同类观测在 15 秒内只记一次。整会话只记一次会让
>   阈值永远攒不满（挂死推不动晋升、成功也撤销不了规则）；每条连接都记则会被
>   一次页面加载的几十条连接刷爆。

界面上落在「分流规则」页的「域名分流规则」卡片：列出每条规则的**证据**
（失败次数、握手成功但无数据的次数、原因、已走隧道流量），并允许逐条撤销或手工指定。

### 已实现：把「握手成功但没有数据」也当成失败

这是实测发现的一类失败，原先**完全不可见**：TLS 握手只用几百毫秒就完成，
随后连接活着 8–10 秒却只交付 0 字节（或零星几百字节）。

它为什么看不见：

* 失败归因只解析含 `ERROR` 的日志行（`core_log.dart`），而这条路径没有 `ERROR`
  ——连接是「建立成功」的，只是没有数据；
* 它又有零星字节，于是按「跑出过任何字节就算成功」的旧判据会被记成**成功**，
  把连续失败计数清零。

对分流决策而言它与连接失败同类。现在的判定规则（`CoreMonitor`）：

| 条件 | 结论 | 依据 |
| --- | --- | --- |
| 字节 ≥ 8 KB | **确实交付** | 实测成功的请求交付 577,137 字节（一次慢的 448,401 字节 / 12.0s） |
| 存活 ≥ 6 秒且字节 < 8 KB | **挂死** | 实测挂死的请求交付 0 字节、存活 8–10 秒 |
| 其余（短命且字节少） | 不下结论 | 可能是一个正常的小响应（实测 raw 的 270 字节就是完整文件） |

**必须联合判断，只看时长会误判**：同一批实测里有一次存活 12.0 秒却交付了
448 KB 的「慢但成功」。

另外，判定发生在连接**关闭之后**：一条连接刚出现时它的字节数还没有意义
（新连接往往只有首包），当时下结论会把「随后会挂住」误判成成功。这也是
`ClashConnection.startedAt` 第一次被真正用起来——它此前被解析但从未使用。

### 已实现：交付速率（第三种证据：能通，但够快吗）

前两种证据都是**二值**的（连接失败、握手成功但零字节），抓不住
「交付了 448 KB 却用了 12 秒」——那在质量判定里算「确实交付」。第三种证据补的
就是这个缺口。

**基准必须是相对的。** 实测本机国内基线只有 337 KB/s，而同一批测量里
github.com 的成功样本是 125–760 KB/s。因此判据是「该域名相对**本session 所有
实质连接的中位数**」，不是任何绝对值。

**刻意不做「同一域名直连 vs 隧道的跨时对比」**：实测 github.com 在 40 分钟内从
40% 成功率变成 100%，两次测量根本不在同一条件下，那种对比得到的是「当时网络好不好」
而不是「哪条路更适合这个域名」。

| 判据 | 取值 | 依据 |
| --- | --- | --- |
| 样本有效性 | 字节 ≥ 64 KB | 更小的传输由慢启动与往返时延主导，算出的速率反映握手过程而非链路水平 |
| 基准 | 全session 连接的速率**中位数** | 中位数抗异常样本；与 DNS 耗时统计同一条理由 |
| 基准最少样本 | 5 | 几个样本当基准会把「今天没跑过大传输」误判成「所有站点都慢」 |
| 「偏慢」 | 低于基准的 **1/4** | 实测同一次 github.com 的两次成功交付相差 20 倍，阈值必须留够间隔 |
| 触发 | **连续** 3 次偏慢 | 与失败晋升同一套迟滞 |

**刻意只设字节下限、不设时长下限。** 一开始加了「至少存活 1 秒」，测试立刻暴露
问题：实测里 github.com 的一个**好样本**是 577 KB / 764 ms，会被那道门槛滤掉——
而它正是应该用来**清除偏慢计数**的正面证据。而它的保护作用是多余的：速率低本身
就蕴含了时长长（2 KB/s 传 64 KB 必然用了 32 秒）。

**两个方向，且回滚条件不同：**

| 情形 | 处置 |
| --- | --- |
| 直连连续偏慢 | 学到 `forceProxy`，并标上 `byRate`（试走隧道） |
| 隧道**同样**偏慢 | 说明问题不在路径上 → 撤销、放回直连，进入**冷却**（30 分钟不重试） |

回滚那一半是为了不把慢域名永久钉在隧道上白耗带宽——而这正是本项目最在意的成本。
而 `byRate` 这个标记是必需的：**因为直连失败**而学到的规则绝不能因为隧道也慢就
放回直连（它在直连上**连不上**）。

冷却期的存在是为了防止来回横跳：没有它就会「直连慢 → 上隧道 → 隧道也慢 → 回直连
→ 直连仍慢 → 又上隧道」。

**一处必须说清的局限**：「偏慢」的阈值（1/4）是本轮**最需要现场校准**的数，
而我没有条件在真实坏窗口里标定它。宁可取得保守（偏慢才触发、间隔留得宽），
也不要因为一次偶然的慢速传输就把域名推上隧道。上表里的样本阈值来自实测，
判据本身有 16 项纯逻辑测试锁定。

### 三个学习方向的仲裁：观测压过推断

三种证据各有独立计数，因此必须明确**谁能否决谁**，否则一个同时满足多条的域名会让
规则来回翻转——用户感受到的就是「分流时好时坏」。

| 证据 | 性质 | 强弱 |
| --- | --- | --- |
| 直连失效 / 握手无数据 | **观测**（试过，没成功） | 强 |
| 交付速率偏慢 | **观测**（成功了，但慢） | 强 |
| 直连解析落在国内网段 | **推断**（地址可能并不可达） | 弱 |

规则是**非对称**的：

| 方向 | 允许？ | 理由 |
| --- | --- | --- |
| 观测 → 覆盖推断 | ✅ 允许 | 实测不通就该走隧道，不管解析落在哪里 |
| 推断 → 覆盖观测 | ❌ **禁止** | 「解析落在国内」不足以推翻「直连实测不通」 |

这条曾经是缺的，后果是**真实的反复弹跳**：一个直连失效的域名被继续送来的
「解析落在国内」翻回直连，再被失效翻回隧道——如此往复。它是被
`app/test/learning_arbitration_test.dart` **复现之后**才修掉的，那一组用例现在
逐步断言「第一次失败攒够阈值之后不再翻转」，而不只看每轮结束时的状态
（上一版只看轮末，于是「中间翻了一轮又翻回来」被漏掉了，而用户感受到的正是中间那一下）。

走隧道规则仍然会被撤销，只是**必须由观测来撤**：

| 撤销路径 | 条件 |
| --- | --- |
| `recordDirectSuccess` | 直连**连续**三次确实交付 |
| `recordDeliveryRate` | 速率规则在隧道上同样偏慢（问题不在路径上）+ 30 分钟冷却 |
| `evictStale` | 14 天无新证据 |

**翻转次数是可见的。** `AutoRouteEntry.flips` 记录走向被程序改过多少次，界面上
在证据那行显示「走向已被程序改过 N 次」。它的意义是把「会不会反复弹跳」从一句
承诺变成用户看得见的事实——而这个项目的原则正是「界面上承诺了什么，代码就必须
真的做什么」。持续增长的条目值得用户手工指定走向，那正是界面已经提供的能力。

`flips` **不参与任何判据**：它只是观测，绝不反过来影响路由，否则会变成一个
「因为我犹豫过，所以我要更犹豫」的正反馈。

### 迟滞的量级：为什么用户不会感到抖

任何一次改判都需要**各自的连续证据**，且各方向的门槛不同：

| 动作 | 需要 | 受什么限流 |
| --- | --- | --- |
| 走隧道（失效/挂死） | 连续 3 次 | 同类观测 15 秒窗口 → **≈45 秒** |
| 走直连（解析落在国内） | 连续 2 次 | 候选探测 30 秒一轮 → **≈60 秒** |
| 走隧道（速率偏慢） | 连续 3 次 | —（速率样本本身就是按连接计） |
| 撤销（直连能用了） | 连续 3 次确实交付 | 同类观测 15 秒窗口 → **≈45 秒** |
| 回滚后重试 | — | **30 分钟冷却** |

也就是说：**一次抖动、一次超时、一次慢传输都不会改变任何路由**。最短的完整翻转
周期（走隧道 → 撤销 → 走直连 → 再走隧道）需要 8 次以上观测。这是「用户无感」的
来源——不是因为它更快，而是因为它**该不动的时候绝不动**。



### 学习机制是一个独立模块

学习相关的**策略、判据与决策**全部集中在
[`app/lib/core/route_learning.dart`](../app/lib/core/route_learning.dart)：

| 内容 | 位置 |
| --- | --- |
| 所有阈值与窗口（`LearningPolicy`） | 该模块 |
| 一次观测算哪种证据（`classifyDirectConnection`） | 该模块 |
| 累计到多少才改判 / 撤销（`judgeSetback`、`shouldRevokeLearnedProxy`） | 该模块 |
| 同类观测的时间窗限流（`OutcomeThrottle`） | 该模块 |
| 规则怎么存、怎么匹配、怎么生成内核语法 | 仍在 `auto_route.dart` 的 `AutoRouteTable` |

**为什么这样切**：未来的迭代只会碰三件事——一次观测算哪种证据、阈值、累计到多少
才改判。三件全是**纯逻辑**，没有一件需要碰路由表的存储、匹配或规则生成。因此把
它们集中到一处之后，迭代学习策略不必动那个承重的表。

这次拆分前，策略常量**横跨两个文件**（阈值在 `auto_route.dart`，判据与限流在
`core_monitor.dart`），后果很具体：想调一个阈值得先想清楚它该在哪个文件；而新增
挂死判据时，因为没有明确的归属地，它就顺手落进了观测层。现在它们在且仅在一个文件里。

`app/test/route_learning_test.dart` 刻意**不引入** `auto_route.dart`：判据与阈值语义
可以在不构造路由表、不伪造网络的前提下逐条验证。如果哪天有人把策略又挪回表里，
那个文件会第一个失败。

需要说明的是这次拆分的**边界**：它把「策略」抽干净了，但 `auto_route.dart` 仍有
1033 行（规则存储 + 匹配 + 历史证据 + 预置安装 + 规则生成）。进一步拆分的成本在
**持久化格式与界面**——历史证据（失败次数、挂死次数、连续计数）目前与规则同存于
`AutoRouteEntry`，界面的证据展示与衰减判定都读它。把证据搬出去会同时改动存档格式、
界面与两端内核调用点，收益不抵风险，因此**刻意停在这里**。

### 已实现：启动自检

用固定探针分别验证「直连」与「隧道」两条腿，从而区分三种表现完全一样、
处置方式却相反的情况：

| 现象 | 结论 | 建议 |
| --- | --- | --- |
| 直连不通、隧道通 | 本地网络或 DNS 有问题 | 不要怪节点 |
| 直连通、隧道不通 | 节点/服务器有问题 | 改规则没有用 |
| 两条都通、个别站点不通 | 规则库覆盖问题 | 交给自动纠正 |

实现见 `lib/core/startup_self_check.dart`，连接后立即跑一次，之后每 10 分钟一次。

## 四点五、DNS 监测与交叉校验

### 为什么必须单独做一层

sing-box 的 `/connections` 快照在**服务端**就把 DNS 流量过滤掉了
（`experimental/clashapi/connections.go` 里的
`metadata.OutboundType != C.TypeDNS`）。因此 DNS 的表现不会出现在连接列表里，
只能主动探测。

### 监测什么

| 指标 | 做法 | 用途 |
| --- | --- | --- |
| 每个解析器的健康度 | 直接向 `223.5.5.5` / `119.29.29.29` 发 UDP A 查询并计时 | 发现某台解析器变慢或不响应 |
| 隧道内解析耗时 | Clash API 的 `/proxies/vpn/delay`，让内核真的经隧道解析并建连 | 用户实际感受到的耗时 |
| 答案交叉校验 | 直连解析器 vs 内核 `/dns/query`，比较两组地址 | 判断是否需要自动纠正 |

统计用**滚动窗口中位数**而不是平均值：一次 3 秒超时能把平均值从 20ms 拉到
100ms 以上，而中位数几乎不受影响。见 `LatencyWindow`。

### 交叉校验的结论

| 直连答案 | 与隧道答案 | 结论 | 处置 |
| --- | --- | --- | --- |
| 在 `geoip-cn` 内 | 不同 | 双部署 | 按域名判定分流是对的，不干预 |
| 不在 `geoip-cn` 内 | 完全不同 | 答案不一致 | 强制走隧道（1 次失败即纠正） |
| 在 `geoip-cn` 内 | 相同 | 一致 | 无需干预 |
| 全失败 | — | 直连解析异常 | 提示检查本地解析是否正常 |

**拿不到地理信息时不下「答案不一致」结论。** `geoip-cn` 前缀索引缺失、或答案全是 IPv6 时，
结论退化为「一致」而不是「答案不一致」——宁可少一次自动纠正，也不要把正常流量推进隧道。

### `geoip-cn` 前缀索引

地理判定需要「这个地址是否落在 `geoip-cn` 内」。`geoip-cn.srs` 是 zlib 压缩的私有格式，
而 Dart 标准库没有 inflate，因此**在构建期**把它摊平成一张紧凑表：

```powershell
pwsh scripts/build-cn-ip-index.ps1
```

（脚本内部用随包分发的 `sing-box rule-set decompile` 反编译，再调用
`app/tool/build_cn_ip_index.dart` 生成。分两步是为了让 Dart 侧只做纯文本转换，
可在任意平台上比对输出。）

产物 `cn-ip.bin` 是 5742 条 IPv4 前缀（45 KB），按网络地址升序排列，运行时二分查找。
IPv6 条目暂未纳入：站点的多线解析以 IPv4 为主，而缺少 IPv6 判定只会让结论
变保守，不会产生错误结论。

> **更新规则库时要记得同步。** 设置页的「检查更新」只替换 `.srs`，不会顺带
> 更新 `cn-ip.bin`。两者不同步会让地理判定与实际分流依据不一致——虽然只会
> 影响新收录网段的判定精度，但既然是一份派生产物，就该一起刷。

## 四点六、直连白名单：一份方向相反的清单

### 为什么规则库不可能解决这件事

分流规则是**白名单式直连**：命中 `geosite-cn` / `geoip-cn` 才直连，其余走隧道
（见 `singbox_config.dart` 的 `_route()`）。而且如第二、三节所示，`geoip-cn` 对
**域名目标**根本不参与判定——因此不在 `geosite-cn` 内的域名**必然**进隧道。

于是有两类「其实能直连」的域名会被误送进隧道，它们都**不可能**被规则库收录，
需要一份方向相反的显式清单：

| 类别 | 为什么规则库收不了 | 默认 |
| --- | --- | --- |
| **国内长尾站点** | `geosite-cn` 是人工维护的列表，覆盖不全（实测 55 个里漏 4 个） | **启用**（把国内站点送进隧道是缺陷） |
| **境外应用**（如 Cursor） | `geosite-cn` 是「中国站点」列表，而这些是境外站点 | 关闭（走隧道才是它们的常态，直连是例外） |

这里最容易误判的地方是：看到「Cursor 走隧道」会以为是**规则库不全**，看到
「国内站点走隧道」会以为 IP 表会兜住。两者都不是——前者规则库不该收，
后者根本没有兜底。

### 实测：Cursor 的域名哪些能直连、哪些不能

2026-09 于中国大陆（深圳）实测。方法：`curl --noproxy '*'` 强制绕过系统代理，
确保测的是直连而不是被本机代理悄悄转了一手。

| 域名 | 直连结果 |
| --- | --- |
| `api2.cursor.sh`（主 API / Chat / 订阅校验） | **200**，TLS 0.52s |
| `api3.cursor.sh`（Tab，Cloudflare） | 404（服务器应答），TLS 0.42s |
| `api4.cursor.sh`（AWS Global Accelerator） | 404，TLS 1.45s |
| `repo42.cursor.sh`（代码库索引） | 404，TLS 0.96s |
| `cursor.com` / `cursor.sh` / `www.cursor.com` | 200 / 308 / 308 |
| `marketplace.cursorapi.com` / `cursor-cdn.com` | 200 / 404 |
| `downloads.cursor.com` / `download.todesktop.com` | 403 / 400 |
| `binaries.s3.us-east-1.amazonaws.com` | 403 |
| `adminportal42.cursor.sh` | 404 |
| **`www.google.com`（负对照）** | **连接超时** |

负对照的意义：它证明上面这些连接**确实是直连**。若测出来的是「被代理转了一手」，
`google.com` 也会通。对照组 fail 而 Cursor 全通，这个测试才有效。

**例外（国内连 DNS 都解析不出，必须留在隧道里）**：

| 域名 | 系统 DNS | `223.5.5.5` | 处置 |
| --- | --- | --- | --- |
| `api5.cursor.sh` | NXDOMAIN | NXDOMAIN | 走隧道（远端 DNS 能解析） |
| `us-asia.gcpp.cursor.sh` | NXDOMAIN | NXDOMAIN | 走隧道 |
| `us-eu.gcpp.cursor.sh` | NXDOMAIN | NXDOMAIN | 走隧道 |

### 为什么例外表必须写对

例外域名（如 `api5.cursor.sh`）正落在直连后缀（`cursor.sh`）的覆盖范围内，
所以：

1. **例外规则必须排在直连规则之前**。内核按顺序**首次命中即生效**，顺序反了
   例外就永远不生效，表现为「大部分 Cursor 功能正常、Agent 打不开」。
2. **NXDOMAIN 不会被自动纠正救回来**。「判为直连却失败」的归因明确排除了
   **解析失败**（见本文第四节），而 NXDOMAIN 正是解析失败。也就是说，一个错放进
   直连的域名会**静默地一直坏着**，程序不会自己学会把它拉回隧道。

### 机制与复核

- 数据在 `lib/core/app_presets.dart`（只放域名清单与实测依据），路由片段由
  `SingBoxConfigBuilder._route()` 统一翻译——与其它规则走同一条路径，不另写一份
  「怎么表达直连/代理」。
- 生成时同时下发 `domain`（精确）与 `domain_suffix`（后缀），因此 `cursor.sh`
  会覆盖 `api2.cursor.sh` 这类子域。这与自动纠正表用的是**同一种写法**，
  其语义（域名字段之间取或、规则之间取先命中）已由自动纠正在生产里验证过。
- 只在**智能分流**下注入。全局代理 / 全局直连是用户显式声明「不要分流」，
  注入域名规则会违背其意图。
- 复核命令（用随包内核校验新形状能被接受）：

```powershell
cd app
flutter test test/singbox_config_binary_test.dart --plain-name "应用直连预置"
```

- 开关在「分流规则」页的「直连白名单」卡片，改动在**下一次连接**时写进内核配置。
  做成开关而不是写死，是因为可达性会随链路与时间变化：写死的话，某天这些域名
  连不上了，用户既看不出原因、也无法关掉它。
- 白名单里有两类，默认值刻意不同：
  * **国内长尾站点补充**（`id: cn-extra`）**默认启用**。它修正的是「国内站点被
    误判进隧道」，那是缺陷而不是配置选项。2026-09 实测：55 个国内站点里 51 个
    被 `geosite-cn` 收录，漏出的 4 个（`gaoding.com`、`jianyu360.com`、
    `gelonghui.com`、`chuangkit.com`）直连解析**全部**落在 `geoip-cn` 网段内。
  * **境外应用预置**（如 Cursor）默认关闭。它们在正常情况下本就该走隧道，
    直连是例外，必须由用户显式启用。
- 存档里出现未知的预置 id 会被忽略（升级后删掉的预置不该让恢复流程出错）；
  存档里**没有** `appPresets` 键时才回退到「默认启用集合」——旧版本存档因此
  也能拿到这项修正。

## 四点七、反方向自动纠正：把「误入隧道」拉回来

### 缺口

第四节描述的自动纠正**只有一个方向**：它观察「判为直连却失败」，把域名推回隧道。
而反方向的错误——**该直连却走了隧道**——不失败、不报错，只是白占隧道带宽、多一跳
延迟，并把访问来源换成境外 IP。也就是说，这个方向的错误原先**既不可观测、
也不可纠正**，而 `AutoRouteTable` 里那条「缺少同等强度的证据」的注释正是承认了这一点。

但这份证据其实已经存在，只是没被用：`dns_monitor.dart` 的交叉校验会拿到
**直连解析器的答案**，而 `cn_ip_index.dart` 的前缀索引可以判断它落不落在国内网段内。

### 判据与门槛

| 证据 | 强度 | 处置 |
| --- | --- | --- |
| 直连解析答案落在 `geoip-cn` 网段内，且该域名当前走隧道 | DNS **事实**；但「因此该直连」是**推断** | 连续 2 次**独立**测量后改为 `forceDirect` |
| 任何一次「判为直连却失败」 | 反证 | 计数清零；累计 3 次则改回 `forceProxy`（原有逻辑） |
| 拿不到地理归属（索引缺失、答案全是 IPv6） | 无结论 | 不动路由 |

关于「独立」：候选探测**必须绕过交叉校验的缓存**（`crossCheck(force: true)`）。
`DnsMonitor` 的缓存 TTL 是 10 分钟，不绕过的话第二次「证据」只是把同一次测量
重读一遍——阈值会变成一个假指标。

另外两个踩过的坑，都由测试锁定：

* 未达到阈值的证据**不建表项**。若按「先建条目再改走向」的老写法，一个
  `preference` 默认为 `forceProxy` 的新条目会立刻变成一条**强制走隧道**的规则
  注入到规则库之前——方向恰好与本证据相反，等于用一条正面证据把它钉死在隧道里。
  因此未定性的证据放在单独的 `_domesticStreak` 里（**不落盘**：它还不是规则，
  不应在用户看不见的地方积累状态）。
* 需要留到下一轮的候选**不能在循环内重新入队**，否则循环的下一次迭代会立刻再探
  同一个域名，「两次独立测量」变成背靠背的两次。

### 驱动与代价

`CoreMonitor.probeDirectCandidates()`，每 30 秒一轮、每轮最多 2 个域名。候选来自
新出现的走隧道连接（`_enqueueDirectCandidate`，队列上限 64，满了丢最旧的）。

每轮对每个候选要占一次隧道往返（交叉校验要问内核），因此刻意做了三重限流：
仅对**有正面证据**的域名留到下一轮（不在国内网段的只探一次）、队列有界、
每轮有配额。IP 目标、已有用户规则的目标、已经是直连的目标都不会入队。

### 可观测：隧道流量去向

`lib/core/tunnel_report.dart` 把已有的逐目标字节数（`SplitRecord.totalBytes`）
汇总成一份按流量降序的清单，回答「隧道带宽被谁占了」，并给出「为什么它在隧道里」
（命中规则库 / 有专门规则 / 默认规则兜底）。界面在「分流规则」页的
「隧道流量去向」卡片，每行可就地「改为直连」（复用 `setDomainPreference`）。

## 四点八、DNS 决策必须跟随路由决策

### 问题

`route.default_domain_resolver` 与 `dns.final` 都指向**隧道**解析器，因此任何
需要内核解析的域名默认都要经隧道问一个境外解析器。而 `dns.rules` 原先**只认
`geosite-cn` 一条**，路由决策却来自三个来源（规则库、自动纠正、直连白名单）。
两份策略由不同的规则集推导，于是会互相矛盾：

| 情形 | 后果 |
| --- | --- |
| 域名已判定**该直连**（白名单预置 / 反方向学到），DNS 却仍走隧道解析器 | 拿到境外 CDN 的地址，再按那个地址直连——判定对了、结果仍错 |
| 域名因**境内答案不可信**被改成走隧道，DNS 却仍被送去境内解析器 | 与判定的依据直接冲突 |

修法不是加一条补丁，而是让 DNS 从**同一个**决策来源派生：
`AutoRouteTable.domainSets()` 给出两组域名，`_dns()` 据此生成两条规则
（强制代理 → `dns-remote`，必须排在 `geosite-cn` **之前**；判定直连 → `dns-cn`）。
顺带消掉了原先在配置生成里另写一份条件的写法——那正是两份策略会分叉的根源。

## 四点九、自检补上「隧道 DNS」探针

### 原先的盲区

自检本来就有一条 DNS 探针，但它用的是 **`www.baidu.com`**——而 baidu 命中
`geosite-cn`，内核按 DNS 规则会用**直连**解析器回答它。也就是说这条探针验证的是
「直连解析能不能用」，**从未碰过隧道解析器**。

而隧道解析器是所有非规则集域名（也就是全部境外站点）的解析出口。它坏了，表现为
「隧道连上了却什么都打不开」，与「节点不通」的外观几乎一样，而处置方式相反。

「隧道出口」那条探针也覆盖不到它：`/proxies/vpn/delay` 访问的是一个**域名**，
代理出站支持域名透传，解析发生在隧道出口那一侧，内核自己的解析器并不参与。

### 补法

新增 `tunnelResolveDomain`（默认 `www.gstatic.com`，**不命中** `geosite-cn`，
因此必然落到隧道解析器），并新增结论分支：

| 探针组合 | 结论 | 建议 |
| --- | --- | --- |
| 隧道通 + 直连解析正常 + 隧道解析失败 | **隧道不通 DNS** | 多半是节点不允许 UDP/53 出站，或隧道内声明的 DNS 不可达；先换一个可达的 DNS，再考虑换节点 |
| 两条解析都失败 | DNS 解析异常 | 问题在 DNS 本身，**不**归因给隧道 |

两者必须分开：两条都失败时归因给隧道，会把用户引向换节点，而换节点没有用。

## 四点十、规则数据源：选谁、为什么、怎么引入

### 评估口径

1. 许可与本项目 **GPL-3.0-or-later** 兼容；
2. 格式与现有机制匹配（`.srs` 最省事：`RuleSetStore` 已有下载、魔数校验、可更新）；
3. 有稳定可版本化的地址；
4. 收录标准与「该不该直连」这个决策一致；
5. 体积与加载代价可接受。

### 实测结论

| 数据源 | 许可 | 格式 | 条目 | 实测 |
| --- | --- | --- | --- | --- |
| **felixonmars/dnsmasq-china-list** | **WTFPL v2**（零条件） | dnsmasq 配置，需构建期编译 | 110448 | 已作为内置补充规则集（默认停用） |
| **MetaCubeX/meta-rules-dat** `@sing` | GPL-3.0 | **`.srs`（直接可用）** | 111022 | 覆盖更全、零回退、负对照全排除；**上游是 GPL-2.0，故不内置**，仅提供地址 |
| v2fly/domain-list-community | MIT | 源码列表 | = 现用 `geosite-cn` | 无增益（它就是现在的来源） |
| `geosite-geolocation-cn` | 同 sing-geosite | `.srs` | 55628 B | **实测与 `geosite-cn` 覆盖率完全相同**（体积只差 14 字节），零增益 |

`geosite-geolocation-cn` 这一条值得记下来：它名字看起来像「更全的中国站点列表」，
很容易被当成现成的升级路径，实测才发现它与 `cn` 是同一份内容。**不要靠名字和
体积推断覆盖率，要实测。**

### 内置的补充规则集：默认启用，依据是实测

`app/assets/rulesets/geosite-cn-extra.srs` 由
`scripts/build-cn-domain-ruleset.ps1` 从 dnsmasq-china-list 编译而来
（110454 个 `domain_suffix`，522 KB）。

**默认启用**。这不是随手取的默认值，而是实测结论：

| 指标 | 方法 | 结果 |
| --- | --- | --- |
| **召回** | 40 个国内站点（含主流与长尾） | **40/40 = 100%** |
| **误命中** | 约 150 个境外域名，含「被墙服务」与「无中国节点服务」两类 | **0 个命中** |

误命中那一栏是真正决定性的：一个被列进这份清单的**被墙**域名会被判成直连，
结果是**直接打不开**。因此样本刻意覆盖了 google / youtube / twitter / facebook /
openai / telegram / discord / reddit / wikipedia / bbc / nytimes / twitch 等
被墙与不便直连的服务——一个都没命中。

还有一道安全网：万一某个被列进去的域名其实不通，它被判为直连后连接失败 →
`suggestsMissingRule` 成立 → 自动纠正表学成「强制代理」，而**学到的规则排在
规则库之前**，因此能覆盖它。也就是说这类错误是**可自愈**的
（DNS 层面的封锁除外，那种情况不会产生连接失败日志）。

其余几个必须记住的点：

* **它不可通过「检查更新」刷新**：上游给的是 dnsmasq 配置而不是 `.srs`，
  程序去下载只会拿到配置文本、被魔数校验拒绝，而报错与用户的网络无关。
  因此 `RuleSetEntry` 增加了 `updatable`，`refreshRuleSet` 跳过这类条目，
  并明确告诉用户「重跑构建脚本」。
* **加载代价可忽略**：用随包内核实测 `sing-box check`，
  55 KB 的 `geosite-cn.srs` 是 75 ms、445 KB 的是 84 ms（3 次取最快）。
* 原先默认启用的 `AppPresets.cnExtra`（4 个实测确认的域名）**保留**：它只有
  4 条，保证「实测到的缺口」在本规则集被用户停用时仍然被覆盖。

### 实测发现的构建缺陷：整个 `.cn` 曾被丢掉

上游**故意不列举** `.cn` 等中文域名，而是靠 dnsmasq 的顶级规则表达：

```
server=/cn/114.114.114.114
server=/top/114.114.114.114
server=/wang/114.114.114.114
server=/xn--55qx5d/…      # 公司
server=/xn--fiqs8s/…      # 中国
server=/xn--io0a7i/…      # 网络
```

它自己的 README 写明了这一点（「不要为已收录的顶级域添加子域，这包括所有
`.cn`——它们已被 `/cn/` 规则匹配」）。**实测：110460 个条目里含 `.cn` 的为 0。**

第一版构建脚本把单标签条目当作「不是域名」跳过了，于是产物**系统性缺失整批
`.cn` 域名**。症状很有迷惑性：40 个国内站点里漏掉的 6 个**全是 `.cn`**，
而它们**能命中** `geosite-cn`，所以不测这一项就完全看不出来。

修法是保留单标签条目——语义与 dnsmasq 完全等价，已用随包内核实测标签边界：

| 输入 | dnsmasq `server=/cn/` | sing-box `domain_suffix: ["cn"]` |
| --- | --- | --- |
| `cn` / `example.cn` / `deep.sub.example.cn` | 命中 | 命中 |
| `notcn` / `foocn` / `cn.example` / `cnn` | 不命中 | 不命中 |

脚本的自检现在会显式断言这三件事（顶级规则存在、标签边界正确、境外域名不命中），
因此这个坑不会重犯。补上后召回率从 **85% 提升到 100%**。

### 域名类规则集必须同时进 DNS 规则

`geosite-cn-extra` 是域名类规则集，因此它必须和 `geosite-cn` 一起出现在
`dns.rules` 里（见「DNS 决策必须跟随路由决策」一节）——内核的一条规则里多个
`rule_set` 之间是**或**关系，一次就能表达「凡是被判为直连的域名都用直连解析器」。

漏掉它**不会报错**，只会表现为「被它判为直连的域名仍被境外解析器解析」，
于是拿到境外 CDN 的地址再去直连——又是「判定对了、结果仍错」。

**「是否域名类」是逐条声明的元数据**（`RuleSetEntry.domainRuleSet`），不是从名字
推断的。演进过程值得记下来，因为它连续踩了两次同一个坑：

1. 最初是 `tag == 'geosite-cn'` 这个硬编码判断。新增 `geosite-cn-extra` 时必然漏掉；
2. 改成由 `BuiltinRuleSet.isDomainRuleSet` 声明后，**自定义条目仍然一律按非域名类**
   处理——而「推荐规则集」（`cn-large`）恰恰走的是自定义路径。也就是说，我们主动
   推荐给用户的规则集，被它判为直连的域名仍经隧道解析，等于从推荐入口把同一个
   问题重新引入。

现在标记随条目走：内置条目在 `builtins` 里声明，推荐项由
`SuggestedRuleSet.domainRuleSet` 带上并**持久化进存档**；手工新增的一律按非域名类
（类型无从得知，不猜）。

存档兼容性有两处要点，都由测试锁定：

* `updatable` 键缺失 → 默认 `true`（旧存档的条目本就都可更新）；
* `domainRuleSet` 键缺失 → **回退到内置定义**，而不是 `false`。旧存档里
  `geosite-cn` 必然没有这个键，若默认 false，升级上来的用户会静默失去
  「命中规则集的域名走直连解析器」这条行为。

### 覆盖更全的那份，走「推荐规则集」而不是内置

ChinaMax 系的覆盖最好，但它的上游 `blackmatrix7/ios_rule_script` 许可是
**GPL-2.0（非 or-later）**——GPL-2.0-only 不能单向升级到 GPL-3.0，再分发进本项目
存在合规灰区。因此本项目**不再分发**它，只在「规则集」页的「推荐规则集」里
给出地址，由用户一键添加（`RuleSetStore.suggested`）。这样既让人能用上，
又不把许可问题带进本项目的分发物。

## 四点十一、分流优先级是一份写进代码的契约

路由规则在配置里的**下标顺序**就是内核的判定顺序（首次命中生效）。这条链原先只
存在于 `_route()` 的函数体里，靠书写顺序表达——任何一次重排都是静默的行为变更，
而最危险的一处从未被写下来：`ip_is_private` 与自动纠正表谁先。

现在它是显式的，并且由 `buildRouteRules()` **按段返回**来保证：

| 顺序 | 规则 | 说明 |
| --- | --- | --- |
| 1 | **用户手工指定** | 最高优先级。用户可以显式把某个内网域名指向代理（例如排查问题），因此它**能覆盖**下一条 |
| 2 | **`ip_is_private` → 直连** | 私有地址段是确定的、可判定的边界 |
| 3 | **程序学到 + 内置白名单** | 由证据推断出来的规则 |
| 4 | **规则库**（`geosite-cn` / `geoip-cn` / `geosite-cn-extra`） | 静态清单 |
| 5 | `route.final` | 兜底：其余走隧道 |

把第 3 段放在第 2 段**之后**修的是一个具体的错误：**内网主机名会落进第 3 段的
证据范围**——

* `nas.local` 解析出 `192.168.x.x` 会被 `geoip-cn` 命中，反方向学习会把它学成
  「直连」（无害）；
* 而它一旦**临时不可达**，就会攒够「直连失败」被推成 `forceProxy`——**有害**：
  内网流量被送进隧道，既费流量又必然连不上，而用户完全看不出原因。

私有地址段不该由推断出的证据去推翻它。用户显式指定则不同——那是人的明确意图，
保留它的最高优先级。

`app/test/app_presets_test.dart` 里有一条用例直接断言这五个位置的下标关系，
因此重排会立刻被测试拦下，而不是等用户发现某类站点坏了。

## 四点十二、运行时与清单质量的实测（含方法）

这一节记录的是**测量方法与结果**，因为「提升了多少」必须能被复核，而不是靠断言。
两个脚本都在 `scripts/` 下，且只用随包内核 + 本地死端口出站，不产生到任何真实
服务器的流量。

### 运行时开销：`scripts/measure-ruleset-runtime-cost.ps1`

此前只量过 `sing-box check` 的耗时（55 KB → 75 ms、522 KB → 84 ms）——那是
**配置校验**，不是运行时。真正的成本在启动时把规则集编译成索引，以及每条连接上的
域名匹配。补测结果（交替采样、交换先后顺序，6 轮 × 200 次请求）：

| 变体 | 就绪 | 常驻内存 | 每请求中位 | p90 |
| --- | --- | --- | --- | --- |
| A：`geosite-cn` + `geoip-cn`（89,688 字节） | 602 ms | 36.0 MB | 13.86 ms | 17.16 ms |
| B：A + `geosite-cn-extra`（612,298 字节） | 574 ms | 37.2 MB | 13.94 ms | 17.28 ms |

体积涨 6.8 倍，代价是约 **1.2 MB 常驻内存**；启动与每请求延迟差异落在噪声内。

**方法上的一个自我纠错值得记下来**：第一次做单次 A/B 配对时得到「B 慢 1.5 ms」，
看起来像真实回退。改成交替采样后该差异消失——那是顺序效应，不是规则集成本。
这正是 `docs/PROTOCOLS.md` §3.5.8 已经写下的标准，第一版没照做。

顺带用数据关掉一条优化路径：`geosite-cn-extra` 与 `geosite-cn` 的重叠仅 **5.06%**
（110454 条中 5585 条已被覆盖），94.94% 是净增，因此「按重叠裁剪规则集」不值得做。

### 清单组成：`scripts/review-cn-ruleset-quality.ps1`

手挑样本只能证明「挑的那些没问题」。因此另做一次**从清单本身随机抽 150 条**
的评测（固定随机种子，可复现）：

| 类别 | 条数 | 占比 |
| --- | --- | --- |
| 解析到国内网段（正确收录） | 96 | 64.0% |
| 未判为国内 | 23 | 15.3% |
| 无解析结果（死域名/停放） | 31 | 20.7% |

两点解读：

* 「无解析结果」的 20.7% 只让清单变胖，不造成误判；
* 「未判为国内」**不必然是误命中**——国内站点也可能托管在境外或用境外 CDN。
  抽样中多个属于国内云网段却被 `geoip-cn` 判为境外，见下节。
* 解析结果区分不出「被墙的境外站点被错列」这一真正有害的情形；那一类由手挑样本
  覆盖（含被墙服务类别，0/150 命中）。

### 附带的发现：`geoip-cn` 整块缺失 `8.0.0.0/8`

`geoip-cn` 的 5742 条 IPv4 前缀里，**`8.x` 前缀为 0 条**——该段包含阿里云的国内
区域地址。用延迟确认这些确实是国内：

| 地址 | 直连 443 耗时 | 归属 |
| --- | --- | --- |
| `8.129.58.15` / `8.134.207.26` | 7 ms | 国内 |
| `8.131.70.224` | 42 ms | 国内 |
| `54.80.103.11`（对照） | 231 ms | 境外 |

**缺口真实但很窄**：38 个主流国内站点解析出的 **146 个 IP 全部命中**。影响面需要
精确限定——域名路由**不受影响**（已证 `geoip-cn` 不参与域名目标的判定）。真正受
影响的是两处：IP 字面量目标会被送进隧道；以及 `classifyRegion` 会把这些地址判为
境外，于是**反方向纠正不会触发**，DNS 交叉校验还可能报出「答案不一致」并据此强制
走隧道。（修复方案见第六节。）

## 五、已实现的观测修正

改造前有几处统计与展示是不准确的，一并记录在这里，因为它们都属于
「界面上承诺了什么，代码就必须真的做什么」：

* **命中规则显示的是内核术语**。sing-box 的 `rule` 字段不是规则名，而是
  `fmt.Sprintf("%s => %s", rule, action)` 拼出来的**描述文本**
  （形如 `rule_set=[geosite-cn geoip-cn] => route`），且 `rulePayload` **恒为空**。
  原实现按 Clash 原版的习惯去读 `rulePayload`，于是「命中规则」这一列实际显示的
  是整句内核术语，而 `switch (rule) { case 'RuleSet': ... }` 那些分支从未命中过。
  现在统一走 `normalizeRuleDescription()`。
* **连接会被重复上报**。原实现在已上报集合长度超过 2000 时整体 `clear()`，
  那一刻「当前活着的每条连接」都会被当成新连接重新上报，分流记录里立刻出现
  成片重复。现在用有容量上限、会按实际连接数自动扩容的 `BoundedIdSet`。
* **只有一个「本次累计」数字**，无法回答「这些流量里有多少真的走了隧道」——
  而那恰恰是判断分流是否按预期工作的唯一依据。现在按出站分别统计。
* **检查行恒为绿色对勾**，于是 DNS 异常、自检发现某条腿不通时界面仍是一片绿色。
  `CheckRow` 现在有 `warn` 态，颜色反映它自己报告的结论。

## 六、尚未实现（按优先级）

1. **补 `geoip-cn` 的覆盖缺口**（本次实测发现）。`8.0.0.0/8` 整块缺失，影响
   IP 字面量目标与 `classifyRegion`（进而影响反方向纠正与 DNS 交叉校验的结论）。
   注意 `cn-ip.bin` 是从 `geoip-cn.srs` 派生的，换源时两者必须同源刷新。
   选项：换一份更全的 CN IP 源（需先过许可审查）、或只补已知缺失的云网段。
2. **反方向纠正的端到端验证**。目前所有用例都注入桩，尚未在真实网络上跑通
   「连续两次独立测量 → 学成直连 → 下次连接生效 → 隧道流量去向里该目标消失」
   这条完整链路。这是当前最大的**未验证**项。
3. **订阅与规则联动**：拿到订阅后按节点地区微调直连策略。
4. **IPv6 的 `geoip-cn` 段判定**：补上后交叉校验在纯 IPv6 环境下也能定性。
   注意它同时是反方向纠正的盲区：答案全是 IPv6 时拿不到地理归属，只能不动路由。
5. **自动纠正的经验共享**：把学到的域名汇总成可选启用的规则补充包。
   反方向纠正（第四点七节）已在本地实现「学一次、以后都记得」，缺的是导出与共享。
6. **清单里的死域名**（约 20.7%）：只让清单变胖，不造成误判。按解析结果过滤会
   引入探测依赖与时效问题，未必值得。
7. **`cn-ip.bin` 与 `geoip-cn` 的派生同步校验**：两者各自更新，可以加一层哈希比对
   让脱同步变成可见的告警，而不是静默的判定偏差。

## 七、已知的假功能（历史）

设置页的「检查更新」曾是一个占位实现：只把显示的日期改成「今天」，
并没有真的下载。这属于误导性界面，已在 `RuleSetStore` 中改为真实实现，
失败时会明确报错而不是假装成功。

留此记录，是为了提醒：**界面上承诺了什么，代码就必须真的做什么。**
